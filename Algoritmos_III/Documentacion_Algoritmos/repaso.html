Bloque 1 — Fundamentos de Web, HTTP y Arquitectura

Antes de comenzar a desarrollar aplicaciones web o APIs en cualquier tecnología, es fundamental comprender cómo se comunican los sistemas y qué arquitectura existe detrás de una aplicación moderna. Muchos problemas de diseño, implementación y mantenimiento aparecen cuando estos conceptos básicos no están claros.

Este bloque introduce tres pilares fundamentales del desarrollo backend:
  • El protocolo HTTP
  • La arquitectura cliente-servidor y el patrón MVC
  • El concepto de API y el estilo REST

El protocolo HTTP

HTTP (HyperText Transfer Protocol) es el protocolo utilizado para la comunicación entre clientes y servidores en la Web. Cada vez que un usuario abre una página, inicia sesión en una aplicación o consulta información desde un frontend, ocurre una comunicación HTTP.

El funcionamiento básico sigue un modelo de petición y respuesta (request/response). Un cliente realiza una solicitud al servidor y este devuelve una respuesta.

Por ejemplo:

  • Un navegador solicita una página web.
  • El servidor procesa la solicitud.
  • El servidor devuelve el contenido correspondiente.

Aunque originalmente HTTP fue diseñado para transferir documentos HTML, hoy se utiliza para prácticamente cualquier tipo de intercambio de información, especialmente en APIs REST.

Estructura de una petición HTTP

Toda petición HTTP posee una estructura bien definida. Comprenderla es esencial para interpretar cómo interactúan frontend y backend. Una petición típica contiene:

  • Un método HTTP
  • Una ruta o URI
  • Headers
  • Opcionalmente un body

Un ejemplo sencillo sería:

POST /productos HTTP/1.1
Host: tienda.com
Content-Type: application/json

{
  "nombre": "Teclado",
  "precio": 15000
}

En este caso, el cliente está solicitando crear un producto nuevo.

Métodos HTTP

Los métodos HTTP indican la acción que el cliente desea realizar sobre un recurso.

  • GET: Utilizado para obtener información sin modificar nada en el servidor. 
    GET /productos
  • POST: Cuando el objetivo es crear un recurso nuevo. 
    POST /productos
  • PUT: Para actualizar completamente un recurso existente. 
    PUT /productos/15
  • PATCH: Si solo se desea modificar parcialmente un recurso. 
    PATCH /productos/15
  • DELETE: Se utiliza para eliminar recursos. 
    DELETE /productos/15

Una parte importante del diseño de APIs consiste en utilizar correctamente estos métodos según la operación realizada.

URI o recurso solicitado

La URI (Uniform Resource Identifier) identifica el recurso sobre el cual se trabaja. Por ejemplo: /productos, /productos/15, o /usuarios/3/pedidos.

En aplicaciones REST modernas, las URIs representan recursos y no acciones. Por ese motivo se prefieren rutas estructuradas:

Correcto: /productos
Incorrecto: /obtenerProductos

La acción ya está expresada mediante el verbo HTTP.

Headers HTTP

Los headers contienen metadatos sobre la petición o la respuesta. Permiten especificar información importante como:

  • El tipo de contenido enviado (Content-Type)
  • El formato esperado
  • Credenciales de autenticación
  • Configuración de caché o idioma preferido

Ejemplos comunes:

Content-Type: application/json
Authorization: Bearer token_de_seguridad

Body de la petición

El body contiene los datos enviados al servidor. Generalmente se utiliza en operaciones de creación o modificación. Actualmente, el formato estándar y más utilizado es JSON.

{
  "nombre": "Mouse",
  "precio": 12000
}

Respuesta HTTP

Luego de procesar la solicitud, el servidor devuelve una respuesta HTTP que incluye un Código de estado, Headers y un Body.

HTTP/1.1 200 OK
Content-Type: application/json

{
  "id": 15,
  "nombre": "Mouse"
}

Códigos de estado HTTP

Los códigos de estado indican el resultado de la operación realizada y se agrupan en familias:

  • 2xx — Operación exitosa: Indica que la solicitud se procesó correctamente.
    200 OK (Éxito), 201 Created (Recurso creado), 204 No Content (Éxito sin cuerpo de respuesta).
  • 3xx — Redirecciones: El recurso solicitado cambió de ubicación.
    301 Moved Permanently.
  • 4xx — Error del cliente: Problemas originados por la propia solicitud.
    400 Bad Request (Sintaxis inválida), 401 Unauthorized (Falta autenticación), 403 Forbidden (Sin permisos), 404 Not Found (No existe el recurso).
  • 5xx — Error del servidor: Fallos internos del propio servidor.
    500 Internal Server Error (Excepción inesperada en el backend).

Statelessness: HTTP es un protocolo sin estado

Una característica fundamental de HTTP es que es stateless. Esto significa que el servidor no recuerda automáticamente solicitudes anteriores realizadas por el mismo cliente. Cada request es independiente y debe contener toda la información necesaria para ser procesado.

Para resolver la persistencia de identidad (por ejemplo, sesiones activas) se implementan mecanismos como:

  • Cookies y Sessions
  • Tokens JWT (JSON Web Tokens)
  • Headers de autenticación dedicados

Arquitectura Cliente-Servidor

La mayoría de las aplicaciones modernas siguen una arquitectura cliente-servidor estructurada bajo dos actores principales:

  • El cliente: Quien consume el servicio (Navegadores web, aplicaciones móviles, frontends en React/Angular, o herramientas como Postman).
  • El servidor: Quien procesa la lógica de negocio, accede a bases de datos y devuelve respuestas.
Cliente → Request HTTP → Servidor
Cliente ← Response HTTP ← Servidor

Separación de responsabilidades (SoC)

Cada componente del sistema debería encargarse únicamente de una tarea específica. El frontend se encarga de la interfaz y experiencia de usuario; el backend procesa reglas de negocio; la base de datos almacena información. Esto permite reducir el acoplamiento, facilitar los tests, mejorar el mantenimiento e incrementar la escalabilidad del sistema.

El patrón MVC (Model-View-Controller)

Es un patrón de arquitectura diseñado para organizar el código separando las responsabilidades de forma explícita:

  • Modelo (Model): Representa los datos, las entidades (Usuario, Producto) y la lógica de negocio junto con el acceso a datos.
  • Vista (View): Representa la interfaz visual (HTML / Plantillas) que se renderiza para el usuario.
  • Controlador (Controller): Intermediario que recibe el request, coordina las operaciones invocando al Modelo y selecciona la Vista de respuesta.
Request → Controller → Model
            ↓
          View

MVC tradicional y aplicaciones modernas

En aplicaciones MVC tradicionales, el servidor genera directamente el código HTML que recibe el navegador (Browser → Servidor MVC → HTML).

Sin embargo, en arquitecturas modernas se opta por separar completamente frontend y backend. El backend ya no devuelve HTML sino datos puros estructurados en formato JSON (Frontend React → API REST → Base de Datos).

¿Qué es una API?

API significa Application Programming Interface. Es una interfaz o contrato que permite que distintos sistemas aislados se comuniquen entre sí de manera estandarizada, definiendo qué operaciones existen, cómo invocarlas y qué estructura de datos se retornará.

APIs REST

REST (Representational State Transfer) no es un protocolo ni una tecnología, sino un estilo arquitectónico basado en un conjunto de principios y buenas prácticas. Las APIs modernas se diseñan bajo principios RESTful:

  • Recursos en REST: Todo gira alrededor de entidades de dominio expuestas en URIs limpias (ej. /productos, /usuarios).
  • Uso correcto de URIs: Las rutas deben representar recursos (sustantivos) y jamás acciones (verbos).
    Correcto: GET /productos, DELETE /productos/15
    Incorrecto: POST /getProductos, POST /deleteCliente
  • Representación de recursos: El estándar universal de transferencia es JSON por ser liviano, legible e independiente del lenguaje emisor/receptor.

Diferencia entre aplicación monolítica y API REST

En un monolito tradicional, el backend maneja la lógica, los datos y la renderización visual en un solo bloque integrado. En cambio, en una arquitectura basada en APIs REST, el backend desacopla la lógica y expone únicamente servicios de datos. Esto permite que múltiples clientes heterogéneos (Web, Apps móviles, sistemas de terceros) consuman la misma lógica de negocio centralizada.

Bloque 2 — Backend con C# y .NET Core

Una vez comprendidos los fundamentos de HTTP, APIs y arquitectura web, el siguiente paso es entender cómo se implementan esos conceptos dentro del ecosistema de .NET. Actualmente, ASP.NET Core es uno de los frameworks empresariales líderes gracias a su alto rendimiento, modularidad e integración nativa con arquitecturas en la nube.

APIs en ASP.NET Core

ASP.NET Core permite exponer endpoints HTTP mediante controladores en C#. Un proyecto Web API típico contiene componentes esenciales configurados desde su inicio.

Program.cs

Es el punto de entrada de la aplicación. En versiones modernas de .NET, centraliza la inicialización de los servicios de inyección de dependencias, la configuración global y el orden de ejecución de la aplicación.

var builder = WebApplication.CreateBuilder(args);

// Registro de servicios en el contenedor de DI
builder.Services.AddControllers();

var app = builder.Build();

// Configuración del pipeline de procesamiento HTTP
app.MapControllers();

app.Run();

El pipeline de Middlewares

ASP.NET Core procesa las solicitudes HTTP entrantes secuencialmente mediante un **Middleware Pipeline**. Cada componente intercepta el request, realiza una tarea y decide si continuar al siguiente paso o cortar el flujo.

Request → Middleware Logging → Middleware Autenticación → Middleware Routing → Controller → Response

Middlewares nativos comunes: Autenticación, Autorización, Manejo global de errores, soporte para CORS y Redirección HTTPS.

Routing por atributos

Es el estilo estándar para mapear URLs directas a métodos específicos de C# mediante decoradores o atributos:

[ApiController]
[Route("api/productos")]
public class ProductosController : ControllerBase
{
    [HttpGet("{id}")]
    public IActionResult ObtenerPorId(int id)
    {
        return Ok(); // Mapea a: GET api/productos/15
    }
}

Controladores en ASP.NET Core

Heredan de ControllerBase, lo que les provee métodos utilitarios para retornar códigos HTTP de manera estructurada (Ok(), NotFound(), BadRequest()).

Para un tipado estricto y documentación clara, se utiliza ActionResult<T>, facilitando que un mismo endpoint maneje respuestas polimórficas (como un 200 con datos o un 404 estructurado).

Inyección de Dependencias (Dependency Injection)

ASP.NET Core incluye un contenedor de DI nativo para resolver el acoplamiento rígido de componentes de software.

El problema del acoplamiento manual:

private readonly ProductoRepository _repository = new ProductoRepository(); (Imposible de testear con Mocks o reemplazar dinámicamente).

La solución mediante Abstracción e Inyección por Constructor:

public class ProductoService
{
    private readonly IProductoRepository _repository;

    public ProductoService(IProductoRepository repository)
    {
        _repository = repository; // Depende de una interfaz, no de una clase concreta
    }
}

Ciclos de vida de los servicios (Service Lifetimes)

  • Transient: Se crea una instancia nueva cada vez que se solicita. Ideal para lógica ligera sin estado.
    builder.Services.AddTransient<IMiServicio, MiServicio>();
  • Scoped: Se crea una única instancia por cada ciclo de vida del Request HTTP. Es el predeterminado para repositorios de datos y contextos transaccionales.
    builder.Services.AddScoped<IMiServicio, MiServicio>();
  • Singleton: Existe una única instancia compartida para toda la aplicación durante todo su tiempo de ejecución. Usado para configuraciones fijas o cachés globales.
    builder.Services.AddSingleton<IMiServicio, MiServicio>();

Patrones de diseño comunes en APIs

Repository Pattern

Abstrae e independiza por completo la persistencia y las consultas de la lógica de negocio. El resto del sistema interactúa con contratos abstractos independientes de la tecnología subyacente (ya sea SQL Server, MongoDB o servicios REST externos).

public interface IProductoRepository
{
    Task<Producto> ObtenerPorId(int id);
    Task Guardar(Producto producto);
}

Unit of Work (Unidad de Trabajo)

Coordina múltiples operaciones transaccionales para asegurar que todas se confirmen como un único bloque atómico (Commit) o bien se cancelen de forma conjunta (Rollback), garantizando la consistencia relacional. Nota: En proyectos que emplean Entity Framework Core, el objeto DbContext ya implementa este patrón de forma nativa.

DTO (Data Transfer Object)

Objetos diseñados con el único fin de transportar datos limpios entre el frontend y el backend, evitando exponer el modelo directo de la base de datos por razones de seguridad, versionado y control de mutabilidad.

// Entidad interna de Base de Datos
public class Usuario { public int Id { get; set; } public string PasswordHash { get; set; } }

// DTO de exposición pública por HTTP
public class UsuarioDto { public int Id { get; set; } public string Nombre { get; set; } }

Bloque 3 — Persistencia y Acceso a Datos con ORMs y Dapper

La capa de persistencia se encarga de resolver la diferencia fundamental entre el modelo de objetos (C#) y el modelo relacional (Tablas SQL), problema conocido en ingeniería de software como el Object-Relational Impedance Mismatch.

¿Qué es un ORM?

Un ORM (Object-Relational Mapping) automatiza la traducción bidireccional entre las filas de una base de datos relacional y los objetos estructurados en memoria dentro de C#.

Enfoques de Acceso a Datos

Característica ORM Pesado (EF Core) Micro-ORM (Dapper)
Generación de SQL Automática mediante traducción de LINQ Manual (Escrito explícitamente por el desarrollador)
Rendimiento Estándar (Posee sobrecarga por Change Tracking) Ultra alto (Cercano a ADO.NET nativo)
Control de Consultas Abstraído por el Framework Absoluto sobre el script SQL ejecutado

Manejo de Datos con Dapper

Desarrollado originalmente por el equipo de **Stack Overflow**, Dapper se inyecta como un conjunto de métodos de extensión sumamente ligeros sobre la interfaz estándar IDbConnection.

Método Query<T> (Lecturas)

Ejecuta sentencias SQL de selección y mapea las columnas del set de resultados directamente a propiedades homónimas del objeto tipado.

using var connection = new SqlConnection(connectionString);
var productos = connection.Query<Producto>("SELECT Id, Nombre FROM Productos");

Método Execute (Escrituras)

Se utiliza para sentencias de manipulación de datos (INSERT, UPDATE, DELETE) que no devuelven filas informativas, retornando el número entero de filas afectadas.

connection.Execute("DELETE FROM Productos WHERE Id = @Id", new { Id = 15 });

Seguridad ante todo: Mitigación de SQL Injection

Dapper obliga e incentiva la parametrización correcta mediante objetos anónimos de C#, evitando por completo la vulnerabilidad crítica de inyección de código malicioso.

Uso Seguro (Parametrizado): 
connection.Query<Usuario>("SELECT * FROM Usuarios WHERE Email = @Email", new { Email = email });
Uso Peligroso (Vulnerable): 
connection.Query<Usuario>("SELECT * FROM Usuarios WHERE Email = '" + email + "'");

Stored Procedures mediante Dapper

Los procedimientos almacenados (código SQL precompilado en el motor) son altamente compatibles y eficientes cuando se ejecutan a través de Dapper parametrizando de forma explícita el tipo de comando:

var producto = connection.QueryFirstOrDefault<Producto>(
    "ObtenerProducto",
    new { Id = 15 },
    commandType: CommandType.StoredProcedure
);

Este enfoque centraliza scripts de optimización complejos directamente en el motor relacional mientras mantiene el código de C# limpio y seguro.
